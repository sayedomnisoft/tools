Stalled system project rescue checklist: 12 checks and the order to restart

For owners and finance heads whose system project has been "almost done" for months. Tick what is true today. The gaps, in the order to fix them, appear underneath.

The short answer

Most stalled system projects did not stall on the software. They stalled on three boring parts nobody inside the business owned: the data, the opening balances and the links to other systems.

To restart: name an owner for each part, freeze new features, sign off the data and balances, test every link with real documents, and only then set a go-live date.

By Sayed Rashid, ex-auditor, 38 systems taken live. Seven-plus years putting Singapore and regional firms onto one system, and rescuing projects that stalled.

A real rescue, anonymised

A private-label apparel group across Singapore, Cambodia and Hong Kong. Their system project had stalled for three years with another vendor. It was rescued and upgraded, and their own in-house software was linked live into accounting.

The lesson: projects die because nobody owns the boring parts: the data, the balances and the links.

The three boring parts, and who should own them

DataOwner: the people who use the lists
  • Products, customers, suppliers and bills of materials, cleaned at the source.
  • One code per item, duplicates merged, units of measure agreed.

Done when: each list is signed off by the person who uses it daily

BalancesOwner: finance
  • Opening stock, receivables, payables and bank.
  • Each agreed to the trial balance at the cut-over date.

Done when: finance signs the opening trial balance

LinksOwner: operations or IT
  • Every place the system talks to another one: web store, payroll, bank files, in-house tools.
  • Tested with last month's real documents.

Done when: the totals agree on both sides

Restart in this order

  1. Name one owner for the project and one for each boring part.
  2. Freeze new features until the open-items list is empty.
  3. Agree and sign off the data and the opening balances.
  4. Test every link with real documents from last month.
  5. Only then set a go-live date, and keep it.

Questions

Why do ERP projects stall?

Usually not because of the software. They stall on the boring parts nobody inside the business owns: cleaning the master data, agreeing the opening balances, and testing the links to other systems. Scope creep keeps the team busy while those parts wait.

How do I know if my system project has stalled?

Two or more of these: the go-live date has moved more than twice, opening balances still do not agree, staff run the old system or a spreadsheet alongside the new one, and meetings are about new features rather than the last open item.

Should we change vendor to rescue a stalled project?

Not as the first step. First find which boring part has no owner. A new vendor inherits the same data, balances and links, so changing vendor without fixing ownership moves the problem rather than solving it.

What is the first step to restart a stalled ERP project?

Name one owner inside the business who can decide, then give the data, the balances and the links an owner each, and freeze new features until the open items are closed.
